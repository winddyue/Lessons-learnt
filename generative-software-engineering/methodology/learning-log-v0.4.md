# 课程记录

## 记录一 AI 原生软件工程

老师试图回答计算能力再次商品化之后，计算机专业人员还能提供什么独特价值。课堂通过浏览器自动化、信息处理工作流、脚本和
Skill 组合等案例，说明 AI
不只是回答问题，而可以把一次成功路径转化为持续运行的能力。

**形成的认识** 软件工程的失败仍然主要发生在 Intent、Specification 和
Implementation
的翻译链上。模型倾向快速完成眼前任务，因此人需要发现值得解决的问题，把未知拆成便宜实验，用证据及时停止坏方向，并对长期结果负责。
S1 00:59 至 01:39

**需要继续观察** 老师认为 AI
当前缺少稳定的工程品位，但也怀疑这种能力可能很快被训练出来。人的长期优势不能建立在模型永远学不会某项能力的假设上。

## 记录二 Git 与版本管理

课堂从目录版本、提交、差异、分支、冲突和历史追溯解释
Git。重点不在背命令，而在理解每次提交代表一次可解释的状态变化。AI
修改速度越快，越需要把变化拆成小而完整的提交。

**形成的认识**
版本管理同时承担三类记忆：当前可工作的状态、走到这里的历史路径、失败和回退留下的教训。
S2 约 00:15 至 01:35 S4 01:29:42 至 01:30:39

**对现有项目的影响** PFMEA Agent 的状态操作、规则调整、交互改版和模型
Adapter 应分别形成可审查变更，不以整包覆盖的方式更新。

## 记录三 Prompt 到 Context Engineering

课堂把 Prompt 从用户输入扩展为完整上下文。System
Prompt、项目与目录级指令、Skills
索引、相关文件、工具定义、工具结果、历史记录和当前用户请求共同影响下一步行为。

**形成的认识** Context 是有限资源。Skill
只在匹配任务时加载完整内容，说明知识库不能简单地把所有资料一次塞给模型。任务应使用最小充分
Context，并在长任务中监控压缩和规则遗失。 S3 00:01:27 至 00:09:35

**对现有项目的影响** PFMEA Context
应分为项目证据、领域知识、组织知识、当前状态和当前
Skill，并根据分析步骤动态装配。

## 记录四 个人助手实验

个人助手 Lab 的真正目标是构建一个持续工作、积累状态并逐步扩展能力的
Agent。课堂同时演示了 One shot Build
的风险：模型严格执行了大量文字，却做出一个看似完整、实际上偏离用户真正需要的系统。

**形成的认识**
从零开始时，应先选一个真实痛点，做最小端到端闭环。数据库、多层业务架构和通用能力可以推迟，先用更直观、容易调整的文件系统获得使用证据。
S4 00:00 至 00:05 01:22 至 01:38

**对个人 AI 工作系统的影响** 随手记 Agent
第一版应先实现可靠录入、可查找和可追溯，不应同时构建完整的任务、报告、邮件和知识图谱平台。

## 记录五 软件工程的来龙去脉

老师从软件危机和早期软件工程方法出发，重新解释需求、设计、实现、测试和维护为什么会被分成不同活动。核心并不是推崇某一种固定流程，而是控制 Intent、Specification 和 Implementation 之间的差距，尽量让错误更早暴露，降低后期返工成本。

**形成的认识** 软件可以理解为一组相互依赖的工程产物。需求、设计、代码、测试和运行证据之间如果没有可追溯关系，就会在变化中发生语义漂移。文档、UML、形式化方法、测试和追踪矩阵，都是历史上为了减少这种漂移而产生的中间机制；AI 可能改变它们的形式，但不会取消“对齐与验证”这一根本问题。 S5 00:45 至 01:39

**对 PFMEA Agent 的影响** PFMEA 不是一张最终表格，而是一张 Requirement、Function、Failure、Cause、Control、Evidence 的依赖网络。Agent 首先要维护关系正确性，再生成展示表格。

## 记录六 需求和架构

课堂把 Git 协作、多 Agent 并行、MVP、需求澄清和架构选择连接起来。老师现场演示了模型严格实现文字要求却没有解决真实痛点的情况，并强调探索期不应被数据库和完整业务架构过早锁定。

**形成的认识** MVP 的价值不是少做几个页面，而是用最低成本检验最关键的意图和风险。架构质量要通过未来变化来测试：需求变化时，修改是否局部、数据是否容易迁移、旧路径是否可以回退。文件系统和 Git 在早期常常比数据库更适合，因为人和 Agent 都能直接检查、比较和重组。 S6 01:15 至 01:39

**对现有项目的影响** PFMEA V0.7 应优先验证 Canonical State、Operation、画板投影和一条完整分析链，不急于建立复杂知识图谱或通用数据库模型。多 Agent 并行前必须先定义工作区、锁定范围和合并协议。

## 记录七 需求和架构二

老师从“软件工程的本质是驾驭复杂性”出发，区分现实业务无法消除的本质复杂度与技术实现额外引入的附加复杂度。随后通过结构化程序设计、抽象与层次、可生长架构、文本接口、MVC 和 MVVM，说明架构的作用不是堆叠框架，而是隔离变化、缩小需要同时理解的范围。

课程后半段用订单、教务和复式记账说明长流程系统的难点：当前状态并不能解释自己是怎样形成的，直接修改数据库中的派生字段会造成静默不一致。Event Sourcing 的核心是保存事实和状态迁移，通过回放得到当前状态，并把依赖关系显式化。 S7 00:03 至 01:39

**形成的认识** 好架构不仅满足当前需求，还应让变化可以追加、影响可以计算、状态可以重放、例外可以解释。抽象不是为了隐藏一切，而是把业务概念、实现细节和变化原因分层，使每一层只承担有限认知负担。

**对 PFMEA Agent 的影响** 当前 Canonical State 仍然必要，但不能成为唯一保存对象。工程师的确认、修改、拒绝、例外批准和规则版本应形成可审计 Operation；正式状态和画板是这些操作经过确定性规则后的投影。这样才能回答某条 PFMEA 为什么存在、由谁确认、依据是什么，以及规则变化后哪些结论需要重算。

## 记录八 跨七课回看老师的思维方式

本次不按课次提取技术知识，而是回看老师反复使用的观察方式。老师理解计算机发展时，关注它如何把昂贵能力变成日用品；理解软件时，关注人的意图和现实规则怎样投影为可执行系统；理解操作系统时，关注抽象和统一接口怎样屏蔽设备差异；理解架构时，关注复杂性、变化和人的认知负担，而不仅是模块名称。

老师学习一个领域时，习惯回到经典文献和历史现场，先问当时的人究竟遇到了什么问题，再用今天的实践重新解释。他并不把教材总结当作终点，因为知识压缩会丢失问题背景、论证过程和取舍。AI 使重新连接“原文—历史—现代案例—个人理解”成为可能。

**形成的认识** 老师的学习方法不是让 AI 替自己读书，而是让 AI 降低进入陌生领域的门槛：先建立地图，再读原文；不懂就持续追问；要求现代案例和反例；最后通过动手实现检验理解。判断、怀疑、选题和品位仍然属于人。

**对我们的影响** 后续课程整理必须同时保存三层内容：老师讲的技术结论、老师得出结论时使用的思维方式、我们在 PFMEA Agent 中的验证。不能再把个人心得留在字幕层。
