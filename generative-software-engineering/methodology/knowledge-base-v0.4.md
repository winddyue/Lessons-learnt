# 当前结论

当代码生成成本大幅下降后，软件工程的瓶颈向上游移动。真正稀缺的是清楚的意图、可执行的规格、能够承受变化的架构、足够而相关的上下文、独立于模型自评的验证证据，以及可追溯的演进历史。软件工程的核心对象也不只是代码，而是需求、设计、代码、测试、运行结果及其依赖关系；任何变更都应沿这张依赖网络评估影响。

# 核心原则

## GSE P001 先明确意图再实现

**原则** 不要让 AI 在目标仍模糊时直接扩大实现。

**理由**
模糊目标会把大量未说明的产品与工程决策交给模型。每个单独决定可能合理，组合后却可能偏离真正需要。

**应用** 开始任务前写清用户 痛点 范围 价值和当前最重要的结果。 S4
01:22:34 至 01:25:08 S1 01:25 至 01:29

## GSE P002 规格管理模型自由度

**原则** 明确哪些决定必须遵守 哪些可以由 AI 探索。

**理由**
凡是没有定义的地方，模型都会通过猜测补全。规格的作用不是写更多文字，而是降低关键部分的任意性。

**应用** 把功能边界 数据结构 接口 约束和验收条件写成可检查项。 S1
01:28:52 至 01:30:38 S4 01:25:02 至 01:26:04

## GSE P003 先稳定架构再扩大规模

**原则** 关键边界和状态责任由人明确，AI 在受控操作空间内扩展。

**理由** 错误架构会随着 AI 的高速度被快速复制。更多代码和更多 Token
不能挽救已经走错的系统。

**应用** 先确定系统边界 状态所有权 变更入口和最小闭环，再增加功能。 S1
01:30:17 至 01:33:32 S4 01:26:16 至 01:28:00

## GSE P004 上下文决定行为

**原则** Agent 的行为由完整 Context 决定，而不是只由最后一句 Prompt
决定。

**理由** System Prompt 项目指令 AGENTS 文件 Skills 工具描述 工具结果
历史记录和用户请求共同参与下一步预测。

**应用** 设计信息的分层 加载时机 优先级和退出机制。 S3 00:01:27 至
00:09:35

## GSE P005 证据先于信任

**原则** AI 声称完成不等于完成，优先使用独立证据判断结果。

**理由** 当任务可被机器验证时，Agent 可以通过执行 失败 修正
再执行形成闭环。模型自评只能作为辅助。

**应用** 为任务提供测试 Schema 校验 规则引擎 基准或人工批准点。 S3
00:20:30 至 00:23:10

## GSE P006 所有重要变化都应版本化

**原则** 保存当前状态 历史路径和失败教训。

**理由** AI 能快速修改大量文件，人更需要知道哪一次变化做了什么 为什么做
以及怎样回退。

**应用**
采用小而完整的提交，提交信息描述意图和结果，失败分支保留必要教训。 S2
00:37:38 至 00:39:10 S4 01:29:42 至 01:30:39

## GSE P007 重复成功应沉淀为 Skill

**原则** 不要每次重新发明 Prompt，把经过验证的方法固化为可复用能力。

**理由** 可复用的不只是代码，还包括完成任务的步骤 证据 工具和边界。Skill
应按任务匹配后再加载完整内容。

**应用** 一次成功后复盘输入 步骤 输出 失败条件和验证方式，再形成 Skill
候选。 S1 01:01:54 至 01:06:00 S3 00:08:05 至 00:08:49

## GSE P008 人负责高层判断

**原则** 当前阶段由人承担意图 取舍 架构 品位和长期结果。

**理由** 模型擅长执行清晰任务，但容易追求表面完成。人需要判断什么值得做
何时停止 哪种结构更可维护。

**应用** 在项目中明确不可委托决策和必须人工批准的节点。 S1 01:36:03 至
01:39:35 S2 00:00:55 至 00:01:10

## GSE P009 管理依赖关系而非孤立产物

**原则** 把需求、设计、代码、测试和运行证据看成相互约束的依赖网络。

**理由** 错误不只存在于某一份文档或某段代码中，更常见的是上下游产物失去一致性。软件工程方法和工具的价值，是降低这种语义漂移，并让变更影响可追踪。

**应用** 为关键需求建立到架构、实现、测试和证据的双向链接；变更时沿依赖关系检查受影响对象。 S5 01:08 至 01:31

## GSE P010 推迟昂贵且难回退的承诺

**原则** 在需求和结构尚未收敛时，优先采用直观、可检查、可迁移的表示。

**理由** 数据库、复杂框架和多层服务可能在成熟阶段有价值，但过早引入会放大迁移和理解成本。文件系统、Git 和明确目录常常更适合探索期，因为人和 Agent 都能直接检查并重组。

**应用** 先证明真实价值和数据形态，再决定持久化、分布式或平台化方案。 S6 01:31 至 01:39

## GSE P011 区分本质复杂度与附加复杂度

**原则** 先承认业务世界无法消除的复杂关系，再减少由工具、表示和实现选择额外引入的复杂度。

**理由** 课程容量、先修关系、订单流程和风险控制属于问题本身；重复转换、隐含状态和不必要的中间层属于实现带来的负担。混在一起处理，会把业务矛盾误判成技术问题，也会用更多技术掩盖错误设计。

**应用** 架构评审时分别列出 Essential Complexity 与 Accidental Complexity；前者通过建模和分解管理，后者通过简化、自动化或删除降低。 S7 00:03 至 00:10

## GSE P012 让派生状态可以重新计算

**原则** 重要结论不应成为无法解释的孤立字段，应能从事实、规则和操作历史重新推导。

**理由** 当前状态只是过去变化的结果。长流程中直接修改派生状态，容易造成局部字段正确而整体关系失真的静默不一致。保留事实和变更历史，可以回放、审计、纠错和评估影响。

**应用** 区分 Source Fact、Operation、Derived State 与 View；关键结论保存来源和规则版本，必要时通过重放重新生成。 S7 01:19 至 01:39

## GSE P013 从根本问题而不是术语学习

**老师原意** 经典文献往往记录一个领域最初遇到、也最重要的根本问题。瀑布模型、结构化程序设计、UNIX 和数据库如果只剩教材标签，就容易被误读。

**我们的提炼** 学习一个概念时先还原问题、约束和历史条件，再看方案、取舍以及今天哪些条件已经变化。不要把后来的标准答案倒灌回原作者。

**PFMEA 应用** 学习 FMEA 手册时不仅记七步法和评分表，还要追问每一步在防止哪种风险遗漏、为什么需要跨职能判断。 S5 00:53 至 01:14 S7 00:14 至 00:31

## GSE P014 穿过抽象层理解系统

**老师原意** 计算机系统通过一层层抽象工作。抽象使人只需处理当前层的问题，但真正理解系统需要能够在用户需求、领域模型、接口、实现和机器行为之间上下移动。

**我们的提炼** 日常工作应停留在合适抽象层，诊断异常时则要有能力向下追到实现、向上回到意图。只懂表面接口或只懂底层细节都不完整。

**PFMEA 应用** 既要在画板上讨论功能和失效，也要能追到 Canonical State、Operation、规则、证据和最终导出。 S1 00:00 至 00:20 S5 00:48 至 01:00 S7 00:20 至 00:49

## GSE P015 AI 扩大探索但不替代判断

**老师原意** AI 可以阅读原文、翻译、总结、找现代案例、回答任意层级的问题，并通过语音保持连续讨论；模型不会嫌弃初学者的重复追问。但模型的品位和方向仍受上下文限制。

**我们的提炼** 把 AI 用作可交互的解释器、研究助手和实验伙伴，而不是最终权威。人仍要选择值得研究的问题、检查原始证据、比较多个解释并用实践确认。

**PFMEA 应用** AI 负责候选、解释和关联，工程师负责确认真实工艺、风险取舍和正式结论。 S3 00:05 至 00:09 01:10 至 01:38 S5 00:43 至 01:05 S7 00:25 至 00:32

# 工作方法

## GSE M001 意图到规格

**适用情形** 需求只有一句话 目标含糊 或团队对完成标准理解不同

1\. 写出目标用户和需要解决的真实问题。

2\. 明确范围之外的内容和当前阶段不做的内容。

3\. 列出关键约束 数据 接口 风险和不可逆决策。

4\. 把完成定义转换成可观察或可验证的验收条件。

5\. 让 AI 复述假设和未决问题，由人确认后再实现。

**输出** 一页规格说明 加假设清单 加验收标准 S1 01:25 至 01:30 S4 01:22
至 01:27

## GSE M002 渐进规格与最小闭环

**适用情形** 从零构建复杂产品 或需求未来可能快速变化

1\. 选择一个真实 高频且可验证的痛点。

2\. 定义最小可用结果，而不是完整功能清单。

3\. 优先使用直观 易调整的结构，推迟数据库和复杂框架等昂贵决定。

4\. 完成一个端到端薄切片并获取使用证据。

5\. 依据证据更新规格，再扩展下一步。

**输出** 可使用的 MVP 加下一轮决策依据 S4 01:32:43 至 01:34:41 S1
01:18:39 至 01:20

## GSE M003 任务上下文设计

**适用情形** Agent 输出不稳定 遗忘规则 或把无关知识混入当前任务

1\. 确认系统级规则和项目级规则。

2\. 只加载当前任务需要的文件 证据和状态。

3\. 通过 Skill 描述暴露可用能力，匹配任务后再读取完整 Skill。

4\. 保留工具结果和当前决策，清理失效或冲突信息。

5\. 在长任务中检查上下文压缩后关键约束是否仍存在。

**输出** 最小充分 Context Package S3 00:01:40 至 00:09:35

## GSE M004 验证循环

**适用情形** 任务结果可以通过程序 规则或结构检查判断

1\. 先定义通过和失败信号。

2\. 让 Agent 生成或修改结果。

3\. 运行独立验证器并保存输出。

4\. 失败时只修改与失败证据相关的部分。

5\. 全部通过后再提交版本并进入下一步。

**输出** 可重复执行的 Generate Execute Test Fix Commit 闭环 S3 00:20:30
至 00:23:10

## GSE M005 小步变更与提交

**适用情形** AI 一次会修改多个文件 或任务需要并行试验

1\. 在变更前确认仓库状态和当前基线。

2\. 把任务拆成一个可说明的逻辑变化。

3\. 执行验证并审查差异。

4\. 用描述意图的提交信息保存变化。

5\. 新方向从可追溯基线分支，不覆盖已有历史。

**输出** 可审查 可回退 可比较的演进记录 S2 00:37 至 01:18 S4 00:30 至
00:40

## GSE M006 Skill 蒸馏

**适用情形** 同类任务已经成功完成两次以上 或人工步骤开始重复

1\. 记录成功任务的输入 环境 工具和输出。

2\. 找出确定性步骤与需要判断的步骤。

3\. 写明适用条件 失败条件和验证标准。

4\. 用新案例试运行并修正。

5\. 只在匹配任务时加载，持续用实际失败更新。

**输出** 可复用 Skill 规格或确定性脚本 S1 00:59:30 至 01:06:00 S3 01:14
左右

## GSE M007 架构与品位审查

**适用情形** 系统看起来已经能运行 但可能过度复杂 偏离目标或难以演进

1\. 从 Intent 和 Specification 反向检查实现。

2\. 检查模块边界 状态所有权 依赖方向和重复能力。

3\. 识别过早抽象 过度设计和难以回退的决定。

4\. 比较更小 更直观的替代方案。

5\. 由人选择取舍，并把理由写入决策记录。

**输出** 架构偏离 风险 技术债和修改建议 S1 01:30 至 01:39 S4 01:25 至
01:34

## GSE M008 可追溯性建模

**适用情形** 系统包含多级需求、设计、实现、测试和审核证据，且任一层都会变化

1\. 定义关键产物及其唯一标识。

2\. 明确产物之间的满足、实现、验证、来源和影响关系。

3\. 为每条关系保留方向、状态和证据。

4\. 变更发生时，从变更点向上下游计算影响范围。

5\. 把断链、孤立要求和无依据结论纳入自动检查。

**输出** 可检查的 Artifact Dependency Graph 和影响清单 S5 01:08 至 01:31

## GSE M009 架构变化测试

**适用情形** 多个方案都能满足当前功能，但未来变化方向不确定

1\. 列出最可能发生的三到五类变化。

2\. 对每个候选架构模拟加入一种变化。

3\. 比较需要修改的模块、数据迁移、接口破坏和回退成本。

4\. 优先选择局部变化、依赖清楚且可回退的方案。

5\. 把取舍和触发重构的条件写入决策记录。

**输出** Architecture Change Matrix 和推迟决策清单 S6 01:34 至 01:39

## GSE M010 复杂度分解与抽象设计

**适用情形** 业务规则多、开发者需要同时理解的信息过多，或修改一个部分会牵动多个模块

1\. 列出业务中无法消除的事实、规则和依赖。

2\. 识别实现额外引入的转换、共享状态和工具负担。

3\. 按职责和变化原因划分模块，并定义最小稳定接口。

4\. 把实现细节封装在抽象内部，让上层使用领域概念而不是底层表示。

5\. 用单元测试、状态可视化和变化场景检查抽象是否真正降低认知负担。

**输出** Complexity Map、模块边界和接口契约 S7 00:03 至 00:31

## GSE M011 事实操作与派生状态建模

**适用情形** 系统包含审批、例外、回退、跨步骤依赖或长期审计要求

1\. 定义不可丢失的原始事实以及事实发生的时间。

2\. 用受控 Operation 表达对事实或正式状态的变更意图。

3\. 明确哪些字段是事实，哪些是根据规则计算的派生状态和展示视图。

4\. 保存规则版本、操作者、理由和证据，使每个结论能够回溯。

5\. 用回放测试验证同一事实序列能否得到相同状态，并用反转事实测试影响范围。

**输出** Event Log、Reducer、Derived State 与 Replay Test S7 01:19 至 01:39

## GSE M012 历史原文到实践的学习闭环

**适用情形** 学习经典概念、进入陌生技术领域，或发现教材结论无法解释现实

1\. 先写出自己真正不理解的问题，不从术语定义开始。

2\. 让 AI 给出知识脉络、关键作者、经典文献和争议点。

3\. 回到原文核查关键结论，区分作者原意、后人解释和自己的理解。

4\. 让 AI 把旧概念映射到现代案例，并主动寻找不成立的反例。

5\. 通过代码、工具或真实项目做一个最小实验。

6\. 记录理解发生了什么变化，以及仍然不能解释的问题。

**输出** Problem Map、原文锚点、现代映射、实验记录和个人解释 S3 01:10 至 01:38 S5 00:53 至 01:14 S7 00:14 至 00:32

## GSE M013 AI 对话式深度学习

**适用情形** 原文较长、背景知识不足，或需要跨多个抽象层连续澄清

1\. 把论文、规范或代码作为共同上下文，而不是只问一个孤立问题。

2\. 先让 AI 概括文章在解决什么问题和整体结构。

3\. 对不理解的概念持续追问，要求换一种解释、举现代案例或画出依赖关系。

4\. 简单问题快速问答，复杂问题让推理模型深入分析。

5\. 对关键事实要求指出原文位置，并用第二来源或实验验证。

6\. 最后用自己的语言复述，让 AI 质疑其中的跳步和误解。

**输出** 可追溯的学习对话、概念图、疑问清单和个人复述 S3 00:05 至 00:09 S7 00:25 至 00:32

# 有效模式

| **编号**      | **模式**                  | **做法**                                            | **解决的问题**               |
|---------------|---------------------------|-----------------------------------------------------|------------------------------|
| **GSE PT001** | Progressive Specification | 先确定关键约束和最小闭环 再逐步补充规格             | 避免模型一次补全大量隐含决定 |
| **GSE PT002** | Thin Slice                | 每轮只交付一个端到端可验证能力                      | 降低集成风险并尽快获得证据   |
| **GSE PT003** | Layered Context           | 系统 项目 任务 Skill 证据分层                       | 降低冲突 遗忘和 Token 浪费   |
| **GSE PT004** | Deterministic Core        | 规则 状态变化和验证使用确定性逻辑 AI 负责候选与解释 | 防止模型自由改写核心状态     |
| **GSE PT005** | Human Approval Gate       | 在意图 架构 高风险操作和正式发布前设置人工确认      | 保留高层责任与风险控制       |
| **GSE PT006** | Reviewable Increment      | 每次提交只表达一个有意义变化并附验证结果            | 让高速 AI 变更仍可理解和回退 |
| **GSE PT007** | Traceable Artifact Graph  | 显式连接需求 设计 实现 测试和证据                   | 防止变更后上下游失去一致性   |
| **GSE PT008** | Isolated Agent Workspace  | 并行 Agent 在独立工作区修改 明确锁定范围后再合并    | 降低高速并发修改的冲突风险   |
| **GSE PT009** | File First Exploration    | 探索期优先使用可读文件和 Git 待结构收敛后再迁移     | 降低早期 Schema 和迁移成本   |
| **GSE PT010** | Growable Architecture     | 保持小而稳定的核心 通过组合 接口和新操作扩展能力     | 让新增需求局部化并减少重写   |
| **GSE PT011** | Fact Operation Projection | 保存事实和操作 由确定性逻辑生成当前状态与视图         | 支持审计 回放 纠错和推演     |

# 反模式

| **编号**      | **反模式**           | **典型表现**                          | **主要后果**                  |
|---------------|----------------------|---------------------------------------|-------------------------------|
| **GSE AP001** | One shot Build       | 把完整复杂需求一次性交给 AI           | 随机架构 隐含假设和快速技术债 |
| **GSE AP002** | Context Dump         | 把所有标准 历史和文件一次性塞入       | 重点稀释 指令冲突和上下文压缩 |
| **GSE AP003** | Self certified Done  | 只接受 AI 对自己的完成声明            | 表面正确但缺少独立证据        |
| **GSE AP004** | Premature Complexity | MVP 阶段先建数据库 多层架构和通用平台 | 迁移成本和心智负担提前出现    |
| **GSE AP005** | Global State Rewrite | 让模型每轮重写完整系统状态            | 不可控丢失 冲突和难以审计     |
| **GSE AP006** | Giant Commit         | 多个目标和大量文件混在一次提交        | 无法审查 定位和局部回退       |
| **GSE AP007** | Prompt Recycling     | 重复复制旧 Prompt 不检查场景和证据    | 把偶然成功误当稳定能力        |
| **GSE AP008** | More Tokens Rescue   | 方向错误后继续加提示 加模型和加 Token | 在错误基础上继续堆积实现      |
| **GSE AP009** | Database First       | 价值和数据形态未验证就先设计数据库与迁移机制 | 早期架构被偶然假设锁定        |
| **GSE AP010** | Artifact Silo        | 需求 设计 代码 测试分别存在但没有关系链接 | 变更影响不可见 错误延迟暴露   |
| **GSE AP011** | Unscoped Agent Parallelism | 多个 Agent 同时修改共享范围且没有锁或责任边界 | 冲突覆盖和责任不可追踪        |
| **GSE AP012** | Mutable Derived State      | 直接修改结论字段 却不保存来源 规则和影响关系   | 状态静默不一致且无法重算      |
| **GSE AP013** | Abstraction Leakage        | 上层必须理解底层存储 流程和实现细节才能工作   | 认知负担扩散 修改牵一发动全身 |

# 术语表

| **术语**                | **当前定义**                                    |
|-------------------------|-------------------------------------------------|
| **Intent**              | 希望解决的问题和期望价值 允许在早期保持一定模糊 |
| **Specification**       | 可执行 可检查的约束 接口 行为和完成标准         |
| **Implementation**      | 满足规格的具体代码 配置 数据和运行系统          |
| **Context**             | 模型当前能够看到并影响下一步行为的全部信息      |
| **Context Engineering** | 设计信息来源 层级 时机 优先级和生命周期         |
| **Skill**               | 在适用条件下可重复执行并带有验证方式的任务能力  |
| **Agent Loop**          | 观察 计划 行动 获取结果 更新上下文 再行动的循环 |
| **Machine verifiable**  | 结果能够由程序 规则或确定性检查产生明确证据     |
| **Taste**               | 对简洁性 边界 取舍 可维护性和长期质量的综合判断 |
| **MVP**                 | 用于验证关键价值和风险的最小可用结果            |
| **Traceability**        | 能够从一个工程产物双向找到其来源 下游实现 验证和变更影响 |
| **Artifact Dependency Graph** | 由需求 设计 代码 测试 证据及其关系构成的有向依赖网络 |
| **Essential Complexity** | 由真实业务事实 规则 例外和依赖决定 无法通过换技术消除的复杂度 |
| **Accidental Complexity** | 由表示 工具 转换 架构和实现选择额外引入的复杂度 |
| **Derived State**       | 根据事实 操作和规则计算得到 可以重新生成的当前结论 |
| **Event Sourcing**      | 保存状态变化事实并通过顺序回放得到当前状态的架构模式 |
| **Abstraction Ladder**  | 在意图 领域模型 接口 实现和机器行为之间上下切换的理解方式 |
| **Knowledge Compression** | 教科书或总结为了传播而对原始知识进行的有损压缩 |
