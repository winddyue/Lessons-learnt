## 这节课真正解决的问题

当需求足够复杂、变化不断发生时，怎样设计一个既能满足当前要求，又不会因为每次修改而逐渐失控的软件系统？

老师的回答不是推荐某个框架，而是建立一条更底层的逻辑：

> 人的认知能力有限；架构要通过抽象、层次、稳定接口和可组合机制，缩小每次需要同时理解的范围，并把变化限制在局部。

课程进一步指出，长流程系统只保存“当前状态”是不够的。现在是过去变化的结果；如果历史、规则和依赖被隐藏，系统就难以解释、纠错和演进。

## 一、从需求进入架构

### 1. Intent、Specification 与 Implementation 的差距

一个意图可以对应多种规格，一个规格又可以对应多种实现。需求工作用于收缩 Intent Space 的不确定性，架构用于收缩 Specification 到 Implementation 的可能空间。

但每一次收缩也是一次承诺：选择数据库、登录方式、数据模型或框架，都会带来长期技术债。因此，面对一个“看起来可以立即实现”的方案，第一反应应当是回头检查：是否存在更简单、更可逆、更能容纳变化的设计。

证据锚点：00:00–14:30。

### 2. 深度优先与广度优先同时存在

- 深度优先：用 MVP 快速验证最重要的需求是否成立。
- 广度优先：对登录、数据、交互、权限等关键选择保留方案空间，理解不同决定的后果。

MVP 不是少做几个页面，而是用一条真实链路暴露 Intent 与实现之间的偏差。

证据锚点：08:00–10:40。

## 二、架构的起点：承认人的“小脑袋”

老师借结构化程序设计的经典材料说明，人无法一次理解任意规模的系统。架构不是为了显得高级，而是尊重人的认知限制。

有效做法包括：

- 把系统分解成可以独立理解的“珍珠”，再通过明确关系串联起来；
- 用抽象恢复代码背后的领域含义；
- 让中间状态可以观察、测试和可视化；
- 通过层次化结构，使每一层只处理本层问题。

动态规划难调试的例子说明：当代码丢失“状态与迁移”的领域抽象，只剩 `dp[i][j][k]` 等底层表示时，人虽然知道算法思想，却无法有效观察程序。好的抽象应把状态含义重新带回实现。

证据锚点：15:00–31:30。

## 三、可生长的架构

课程通过 Guy Steele 的 *Growing a Language* 引出关键判断：

> 好架构不是一次性实现完整需求清单，而是让扩展成为一等公民，并让扩展之间能够组合。

过小的语言容易实现和移植，但表达能力不足；一次设计一个庞大语言，又会交付缓慢并被更小的方案取代。出路不是二选一，而是让系统能够生长。

对软件系统同样如此：

- 核心应尽量小而稳定；
- 新能力通过明确接口、词汇和操作加入；
- 局部扩展不应要求重写整个系统；
- 组合机制比不断增加特殊开关更重要。

证据锚点：34:00–49:30。

## 四、经典架构为什么能够穿越时间

### UNIX：统一接口带来组合性

UNIX 工具“只做好一件事”，并通过文本流、管道、统一参数和退出状态组合。关键不只是工具小，而是人和程序共享了一套可理解、可组合的接口。

### 关系数据库：隔离数据表示

关系模型把现实世界抽象为表和关系，通过 SQL、事务和视图隔离底层存储，使应用能够专注业务。这套架构支持不同领域定义自己的 Schema，因此具有巨大的扩展空间。

### Internet：稳定核心承载未知应用

网络核心集中解决 Connectivity，不预设上层应用。稳定规则允许上层协议和应用不断变化，说明“唯一持久的原则是变化本身”。

三个案例的共同结构是：

```text
小而稳定的核心
＋ 清楚的接口
＋ 可组合的操作
＋ 把局部变化留给上层
＝ 可生长的生态
```

证据锚点：49:30–64:00。

## 五、从 MVC 到前端状态

以数据库为中心的信息系统，可以把：

- Model 理解为当前世界的知识；
- View 理解为 Model 的可视化投影；
- Controller 理解为用户触发状态变化的入口。

当页面拥有搜索框、悬停、展开菜单等临时状态时，数据库 Model 已不足以表示全部交互，于是出现 MVVM、React 和 Vue 等不同解决方案。它们虽然机制不同，但都在尝试：

- 分离数据源、逻辑和显示；
- 显式管理依赖；
- 让界面成为状态的函数；
- 把增量更新的复杂性封装在框架内部。

证据锚点：64:00–79:00。

## 六、长流程系统为什么会失控

订单、教务、风控、毕业审核等系统既要表达过去，又要表示现在，还要决定未来。当数据库只保存当前状态时，例外批准、人工修改、规则升级和程序缺陷可能让字段之间静默失去一致性。

例如，一门先修课成绩被事后改为不及格，会同时影响后续选课、学分和毕业资格。只修改成绩字段，无法保证所有派生结论同步变化。

这不是简单的数据库 Bug，而是业务本身存在复杂依赖；架构必须把这些依赖暴露出来。

证据锚点：79:00–85:30。

## 七、Event Sourcing：保存变化，而不仅是结果

Event Sourcing 的核心不是“多一张日志表”，而是改变系统事实的定义：

1. 保存实际发生的事实或操作；
2. 由确定性规则按顺序处理这些事实；
3. 当前状态是操作历史的投影；
4. 规则或解释错误时，可以修正规则并重放；
5. 新需求和例外通过追加事实表达，而不是手工篡改派生字段。

它不能消除业务的本质复杂度，但能把事实、规则、派生状态和视图分开，使系统具备：可追溯、可审计、可重放、可纠错、可推演未来、可计算变更影响。

证据锚点：85:30–99:40。

## 老师示范的思维方式

### 1. 从历史现场理解概念

老师不把“结构化程序设计、UNIX、关系数据库、MVC”当作需要记忆的术语，而是回到这些设计诞生时的问题：当时什么能力缺失？人的限制是什么？为什么这个抽象能够成立？

### 2. 在抽象与实例之间往返

课程从“驾驭复杂性”下沉到登录、动态规划、模板语言和教务数据，再上升为抽象、接口、组合、状态和依赖。理解不是停在任何单一层级，而是能够上下穿行。

### 3. 用变化检验架构

“当前能够运行”不是架构质量。更重要的问题是：规则变了怎么办？增加一种例外怎么办？状态出错能否解释？影响范围是否可计算？

### 4. 用 AI 重建个人学习路径

AI 可以帮助检索经典文献、阅读原文、翻译、解释、寻找现代案例，并在语音对话中持续追问。但有效学习仍从已有知识出发，向外扩展一个问题，再把新知识连接回个人知识网络。

### 5. 警惕“新”和“多”对品位的污染

大量新论文、技术文章和 AI 生成内容不等于更好的知识。经典工作的价值在于它们直接面对一个领域最根本的问题；AI 的价值之一，是让普通学习者能够重新接近这些一手思想。

## 对 PFMEA Agent 的直接影响

### 已验证的方向

- `Canonical State` 必须保留，它是当前正式分析结果的统一投影。
- `Operation` 不能只是技术实现细节，它应记录确认、修改、拒绝、撤销、例外批准及其证据。
- 画板是状态的 View，不应成为独立事实来源。
- AI 生成的是 Candidate；工程师确认后才形成正式 Operation。

### 需要补齐的能力

1. 每条 Operation 保存操作者、时间、理由、证据和规则版本。
2. 建立 Reducer，用同一操作序列稳定重建 Canonical State。
3. 对 Requirement 撤销、规则升级和例外批准建立 Replay Test。
4. 显式记录 Requirement → Function → Failure → Cause → Control → Evidence 的依赖。
5. 区分 Project Fact、Domain Rule、Derived Assessment 和 UI View。

### 一个重要边界

PFMEA Agent 不需要为了追随 Event Sourcing 而立即重建全部系统。第一步应验证最小闭环：

```text
端子压接事实
→ AI 候选
→ 工程师确认
→ Operation
→ Canonical State
→ 画板与 Excel 投影
→ 撤销或规则变化后的重放
```

这符合课程反复强调的原则：先通过最小真实链路暴露问题，再决定需要多大的架构。

## 本课留下的开放问题

1. 哪些 PFMEA 输入属于不可丢失的事实，哪些只是当前规则下的派生结论？
2. 工程师修改历史事实时，应追加更正事件，还是允许修改原事件？
3. 规则升级后，旧 PFMEA 应按原规则保留，还是生成新投影？
4. Event Sourcing 带来的复杂度何时大于它解决的问题？
5. 哪些依赖必须显式建模，哪些可以在计算时临时推导？

## 本课提炼的一句话

> 架构不是把今天的需求安放整齐，而是让明天的变化仍然能够被理解、被控制、被追溯。
